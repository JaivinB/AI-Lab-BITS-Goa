# Lab 3 — Search and A*

A warehouse robot must move from the loading area `S` to the delivery area `G`,
one cell at a time, at cost 1 per move. The scientific idea is search; A* is one
algorithm implementing it; the LLM is an engineering tool. Verifying the result
stays the engineer's job.

| `tests_and_experiments.py` | Task 3 tests, the BFS/A* comparison, and the heuristic investigation |


Pure Python 3, no dependencies.

## Task 0 — The search problem, before any code

| Component | Specification |
|---|---|
| States `S` | The robot's cell, `(row, column)`, for every cell that is not an obstacle. 64 reachable cells on this map, all of them reachable from `S`. |
| Actions `A` | `{Up, Down, Left, Right}`, each a `(dr, dc)` offset of one cell. |
| Transition `T` | `T(s, a) = s + delta(a)`, defined only when the target cell is inside the grid and is not `#`. Otherwise the action is unavailable in `s`. |
| Initial state `s0` | `(1, 1)`, the cell marked `S`. |
| Goal `G` | `{(7, 15)}`, the single cell marked `G`; goal test `s == (7, 15)`. |
| Cost `c` | `c(s, a) = 1` for every state and action. Plan cost = number of moves. |

**(a) What information is necessary to specify a state?** The robot's position
and nothing else. The map is static, the robot carries nothing that affects
movement, and no action has a lasting side effect, so position alone determines
which actions are available and what they do. Were there doors to open or a
payload affecting mobility, the state would have to be extended, and the state
space would grow multiplicatively.

**(b) What makes an action invalid?** Its destination cell failing `passable()`
— either outside the grid, or an obstacle. Validity is a property of the
*destination*, not of the action, so each action is valid in some states and not
others.

**(c) Is this a deterministic search problem?** Yes. Each `(state, action)` pair
has exactly one outcome, the map never changes, and nothing is hidden. So a plan
computed entirely offline can be executed without re-planning — which is what
makes it legitimate to search first and move afterwards.

**(d) What would constitute a solution?** A sequence of actions that is
applicable from `s0` in order, every intermediate state being a free cell, ending
in a state that satisfies the goal test. A *shortest* solution additionally
minimises the number of moves; since every move costs 1, minimal length and
minimal cost coincide here.

## Task 1 — Agent design, before prompting the LLM

1. **State in Python** — a `(row, column)` tuple. Immutable, hashable, so it can
   be a dictionary key and a set member, which the closed set and the
   predecessor map both need.
2. **The warehouse** — a list of lists of characters, parsed once from the ASCII
   map, with `S` and `G` located at construction. Exposed only through
   `passable()`, `successors()` and `is_goal()`, so the search never indexes the
   grid directly.
3. **Valid actions** — generated by `successors()`, which applies all four
   offsets and yields only those whose destination is passable, together with the
   action name and the step cost.
4. **Recognising the goal** — an explicit `is_goal(state)` predicate, tested when
   a state is *expanded* rather than when it is generated.
5. **What the frontier must store** — for BFS, just the state, because depth is
   implicit in the queue order. For A*, the state and its `f(n)`, plus a
   tie-break key; `g(n)` is kept in a separate `g_score` map so a cheaper route
   to an already-seen state can be recognised.
6. **Reconstructing the path** — a `came_from` dictionary mapping each reached
   state to `(predecessor, action)`. On success, follow the links back from the
   goal and reverse. This stores the search tree rather than a path per frontier
   entry, which is what keeps memory proportional to states reached.

**What the program reports on termination:** whether a solution was found, the
solution path, the path length, and the number of states expanded. Two more were
added because they turned out to be necessary to interpret the results: the
number of states *generated*, and the peak frontier size — the latter is what
eventually explained why A* and BFS tie on this map.

## Task 4 — Where each concept appears in the code

| Concept | Where it appears in `search_agent.py` |
|---|---|
| State | `(row, column)` tuples throughout; created in `Grid._find` (line 62) and `Grid.successors` (line 75) |
| Action | `ACTIONS`, the name → offset table (line 33); yielded by `successors` |
| Transition | `nxt = (r + dr, c + dc)` guarded by `passable(nxt)` in `successors` (lines 75–81) |
| Goal test | `Grid.is_goal` (line 83), called on expansion at line 221 |
| `g(n)` | `g_score`, initialised at line 212, extended as `tentative_g` at line 232 |
| `h(n)` | `manhattan` and friends (lines 97–125); called at line 237 |
| `f(n)` | `tentative_g + h`, the first element of the heap entry (line 240) |
| Frontier | `heapq` list of `(f, tie key, counter, state)` (line 210) — a FIFO `deque` in BFS (line 165) |
| Visited states | `closed` set (line 214), plus `g_score` as the reached set |
| Path reconstruction | `_reconstruct` (line 146), following `came_from` back from the goal |

**(a) What data structure is used for the A* frontier?** A binary min-heap
(`heapq`) of tuples `(f, tie key, insertion counter, state)`.

**(b) How does the program select the next state to expand?** `heapq.heappop`
returns the entry with the smallest `f`. Because tuples compare
lexicographically, equal `f` falls through to the tie key and then to the
insertion counter, so the order is fully determined and reproducible.

**(c) Where is the heuristic calculated?** At line 237, once per successor, as
`heuristic(nxt, grid.goal)` — not stored on the state, so swapping the
heuristic changes one argument and nothing else.

**(d) Does the program explicitly calculate `f(n) = g(n) + h(n)`?** Yes, at line
240: `tentative_g + h`, where `tentative_g = g_score[state] + step_cost`. Both
terms are visible as separate quantities rather than folded into one priority.

**(e) How does the program prevent unnecessary repeated exploration?** Three
mechanisms. A `closed` set records states already expanded, and successors in it
are skipped. A stale-entry check on pop discards a heap entry for a state that
has since been closed, which is needed because the heap can hold several entries
for the same state. And `g_score` means a successor is only re-pushed if the new
route to it is strictly cheaper. As generated the code had none of these; see
`prompts.md`, correction 1.

## Task 5 — A* compared with blind search

Warehouse unchanged, same `Grid` and successor function for both algorithms.

| Measure | BFS | A* (Manhattan) | A* + goal-directed tie-breaking |
|---|---|---|---|
| Solution found | yes | yes | yes |
| Path length | 40 | 40 | 40 |
| **States expanded** | **63** | **63** | **63** |
| Peak frontier | 3 | 3 | 3 |

**(a) Did both algorithms find a solution?** Yes.
**(b) Paths of the same length?** Yes, 40 moves, and both optimal.
**(c) Which expanded fewer states?** Neither — an exact tie at 63.
**(d) Why might A\* expand fewer states?** Because `f(n) = g(n) + h(n)` lets it
ignore states whose *total* estimated cost already exceeds the best known
complete solution, so it never expands a state with `f(n) > f*`. BFS orders by
`g(n)` alone and so expands every state at depth `< d` before any at depth `d`,
including states leading directly away from the goal.

**But that is not what happened here, and the reason matters.** The peak frontier
of 3 is the clue: this map is almost entirely single-width corridor, so at nearly
every step there is exactly one successor. A heuristic can only help by
*reordering choices*, and this map offers almost none. A* is not better merely
for being better informed — it is better only when there is a decision for the
information to inform.

To test that explanation rather than assert it, the same two algorithms were run
on an open floor of comparable size:

| Measure | BFS | A* (Manhattan) | A* + goal-directed tie-breaking |
|---|---|---|---|
| Solution found | yes | yes | yes |
| Path length | 19 | 19 | 19 |
| **States expanded** | **89** | **89** | **19** |
| Peak frontier | 6 | 6 | 18 |

A* with Manhattan distance *still* ties with BFS at 89 — nearly the whole floor.
This is neither a bug nor a bad heuristic. On a unit-cost grid, every cell on
every monotone staircase from `S` to `G` has `f(n) = 19` exactly, the optimal
cost. Admissibility guarantees A* never expands a state with `f > f*`; it says
nothing about states with `f = f*`, and here almost every free cell is one.
Insertion order then fans out exactly like BFS.

Breaking `f`-ties towards the goal — prefer the smaller `h(n)` — cuts expansions
from 89 to 19, a factor of 4.7, returning the same optimal 19-move path.
Optimality is untouched, because neither rule ever expands a state with
`f > f*`. The textbook claim that "A* expands fewer states" is therefore
conditional on two things the lecture does not emphasise: that the map offers
choices, and that ties are broken sensibly.

## Task 6 — Investigating the heuristic

**Why Manhattan distance is appropriate here.** The robot moves only
horizontally and vertically, one cell per move, at cost 1. Reaching the goal
therefore takes at least `|dx| + |dy|` moves, so Manhattan distance never
overestimates the remaining cost — it is admissible — and it is *exact* on an
empty floor. Obstacles can only lengthen the true path, never shorten it, so
admissibility survives them. Diagonal movement would break this: with diagonal
steps at cost 1, Manhattan distance would overestimate and Euclidean would become
the admissible choice.

Expansions are reported under both tie-breaking rules, because on a unit-cost
grid the tie rule matters as much as the heuristic.

**Warehouse from the laboratory sheet:**

| `h(n)` | Solution | Length | Expanded (insertion / goal-directed) | Optimal? |
|---|---|---|---|---|
| Manhattan | yes | 40 | 63 / 63 | yes |
| `h = 0` | yes | 40 | 63 / 63 | yes |
| Euclidean | yes | 40 | 63 / 63 | yes |
| `2 ×` Manhattan | yes | 40 | 63 / 63 | yes |

Every variant is identical, and 63 is every reachable cell but the goal: each
search exhausts the map before finding `G`. Even `h = 0` — no information
whatsoever — costs nothing, because there is essentially one route to find. **No experiment run on
this warehouse alone could distinguish a good heuristic from a useless one**,
which is the most important methodological result in the lab.

**Open floor, where the search has choices:**

| `h(n)` | Solution | Length | Expanded (insertion / goal-directed) | Optimal? |
|---|---|---|---|---|
| Manhattan | yes | 19 | 89 / **19** | yes |
| `h = 0` | yes | 19 | 89 / 89 | yes |
| Euclidean | yes | 19 | 89 / 71 | yes |
| `2 ×` Manhattan | yes | 19 | **19** / 19 | yes |

- **`h = 0`** — A* degenerates to uniform-cost search. It carries no
  information, so it cannot even break a tie, and the tuned column is identical.
- **Euclidean** — admissible, but on 4-connected moves it underestimates by more
  than Manhattan (`sqrt(dx² + dy²) ≤ dx + dy`), so it is the weaker of the two
  admissible heuristics: 71 against 19.
- **Manhattan** — exact on an open floor; with goal-directed tie-breaking it
  expands only the 19 cells of the path itself, the theoretical minimum.
- **`2 ×` Manhattan** — fewest expansions, and it needs no tie-breaking, because
  inflating `h` destroys the ties.

The ranking by expansions follows the ranking by how much the heuristic knows,
which answers the lab's question: *what information does the algorithm use to
decide where to search next?*

**What an inadmissible heuristic costs.** On both maps above, `2 ×` Manhattan
returned an optimal path anyway. That is itself the warning — a broken heuristic
can look perfectly fine on the maps you happen to test. On a layout with
genuinely competing routes it fails:

| `h(n)` | Length | Expanded (insertion / goal-directed) | Optimal? |
|---|---|---|---|
| Manhattan | 18 | 55 / 48 | yes |
| `h = 0` | 18 | 61 / 61 | yes |
| Euclidean | 18 | 55 / 46 | yes |
| `2 ×` Manhattan | **22** | **39** / 36 | **no (+4)** |

`2 ×` Manhattan expands fewest — 39 against 55 — and returns a 22-move path
where the optimum is 18. That is the trade precisely: inflating `h` buys search
effort with solution quality. Weighted A* with weight `w` returns a path no worse
than `w` times optimal, and `22 ≤ 2 × 18` respects the bound.

So: **too optimistic** a heuristic (`h = 0`) is safe but slow — it still finds
the optimum, it just explores more. **Too aggressive** a heuristic is fast but
can be wrong, and the error is *silent*: the program prints a perfectly valid
path, merely not a shortest one. Only a test that knows the true optimum detects
it, which is why Test 4 was constructed with two routes of known length.

## Task 7 — Evaluating the LLM-generated agent

**1. What was correct immediately?** The overall skeleton: the `heapq` frontier,
the `came_from` dictionary and backward path reconstruction, the Manhattan
heuristic, the map parsing, and the `g`/`h`/`f` arithmetic being written out
explicitly rather than folded into a single priority. The program ran on the
first attempt and printed a correct 40-move path.

**2. Any bugs or design problems?** Six, listed in `prompts.md`. The three that
mattered: no closed set and no stale-entry check, so with an inconsistent
heuristic states are expanded repeatedly and the "states expanded" figure —
the very measurement Tasks 5 and 6 compare — becomes meaningless; the goal test
applied on *generation* rather than expansion, which is wrong in general for A*;
and a Euclidean heuristic implemented as the *squared* distance, which is
inadmissible and would have silently broken optimality while being presented as
the admissible alternative.

**3. How were they discovered?** Not by running the original warehouse — that
map returns 40 moves and 63 expansions under every variant, correct or broken.
They were found by reading the code against the specification, and by building
tests whose answers were known beforehand. The squared-Euclidean bug in
particular is invisible on a corridor map and only shows up where the heuristic
has choices to misorder.

**4. Terminology or data structures that were unfamiliar?** The tuple-ordering
trick on the heap — relying on Python comparing the second element when the
first ties — was initially unclear and is genuinely subtle: the generated code
pushed `(f, state)`, which silently compares `(row, col)` tuples on ties and
biases the search towards low row indices. Making the tie key explicit was both
a correctness fix and the thing that made Task 5's tie-breaking experiment
possible.

**5. Was the code modified?** Yes, in all six places listed, plus the addition
of `verify()`, the expanded/generated/peak-frontier counters, and the
tie-breaking option. The algorithm's structure is the LLM's; the correctness of
the closed set, the goal test, the heuristics, and every measurement reported
here are not.

**6. Which tests were most useful?** Test 4 (two routes of known length), because
it is the only one that can distinguish "found a path" from "found a shortest
path". Then the inadmissibility experiment, which is what demonstrated the
difference between a heuristic that is weak and one that is wrong. Test 1 was the
least useful, despite being the lab's main map.

**7. Could the program have been trusted without testing?** No — and the
interesting part is that testing it only on the supplied warehouse would have
been no better than not testing it. That map cannot distinguish BFS from A*, a
good heuristic from `h = 0`, or an admissible heuristic from an inadmissible one.
Every variant returns 40 moves and 63 expansions. Confidence came from maps
chosen to be able to fail.

**8. What was understood about A\* only after implementing it?** That
admissibility is a statement about which states A* *cannot* expand (`f > f*`),
not about which it *will* expand — and that on a uniform-cost grid the set of
states with `f` exactly `f*` is so large that an admissible, even exact,
heuristic can give no benefit at all unless ties are broken deliberately. Before
implementing it, "A* expands fewer states than BFS" seemed like a property of the
algorithm. It is actually a property of the algorithm, the map, and the tie rule
together.

## Final reflection

**1. Why formulate the search problem before writing the algorithm?** Because
the formulation determines whether an algorithm is even applicable. The
observation that every action costs 1 is what makes BFS optimal and Manhattan
distance admissible; neither claim survives varying terrain cost. Writing
`(S, A, T, s0, G, c)` down first also exposes decisions that code hides — that
position alone suffices as state, and that an action's validity is a property of
its destination. Had the state needed to include a payload or a battery level,
discovering that after generating code would have meant discarding it.

**2. In what sense is A\* "informed"?** It uses information not contained in the
graph: an estimate `h(n)` of the cost still to come. BFS and uniform-cost search
know only where they have been, so they order the frontier by `g(n)` and spread
outwards in all directions. A* orders by `g(n) + h(n)`, so it accounts for the
whole journey and can decline to expand states whose total estimated cost already
exceeds a known solution. The experiments add a qualification: being informed
only pays where the search faces choices, and `h = 0` turns A* back into
uniform-cost search exactly.

**3. Why does the choice of heuristic matter?** It controls both correctness and
cost. An admissible heuristic preserves optimality, and among admissible
heuristics the more accurate one expands no more states — Manhattan beat
Euclidean 19 to 71 for this reason. An inadmissible heuristic trades the
optimality guarantee for speed: `2 ×` Manhattan was the fastest variant tested
and returned a path 22% too long. The failure is silent, so the heuristic's
admissibility must be *argued*, not assumed from the fact that the program
produces a path.

**4. What did the LLM contribute?** It converted a written design into working
PyTorch-free Python in one pass — the heap mechanics, the predecessor-map
reconstruction, the map parsing, the output formatting. That is a genuine saving
on the parts where the right answer is conventional and well documented. It also
suggested the `heapq` tuple-ordering idiom, which turned out to be the hinge of
the whole tie-breaking investigation.

**5. What could go wrong if LLM-generated code were accepted untested?** All
three serious bugs here would have survived, and none would have announced
itself. The program would have kept printing valid-looking 40-move paths. The
squared-Euclidean heuristic would have been reported as "admissible, slightly
weaker than Manhattan" in a results table — a fabricated finding, derived from a
real measurement of the wrong thing. Code generation moves the risk from "does it
run?" to "is it answering the question I asked?", and only tests with known
answers can tell the difference.
